# Gate WebAssembly Plugin Support

Date: 2026-07-28

Status: Approved

## Summary

Gate will load language-neutral WebAssembly Components as plugins. A plugin will
receive equivalents of Gate's existing `context.Context` and
`*proxy.Proxy` during initialization and will be able to call Gate's public Go
API through statically generated bindings.

The public contract will be generated from Gate's Go source. There will be no
hand-maintained list of wrapper methods and no Gate-maintained SDK for each
guest language. Gate will publish a WIT contract; plugin authors will use
standard WIT tooling for Go, Rust, TypeScript, or any other supported language.

The host will embed Wasmtime through a small statically linked Rust library and
a generated CGO bridge:

```text
Gate Go API
    ↕ generated Go dispatchers and C-compatible layouts
Rust Wasmtime host
    ↕ generated Wasmtime Component Model bindings
WIT contract
    ↕ guest-language bindings generated by standard WIT tools
WebAssembly Component
```

This architecture is required because the current Wasmtime Go binding does not
yet provide the host-side Component Model linker and typed component function
calls needed by Gate. The Rust Wasmtime API does.

## Goals

- Give WebAssembly plugins the same lifecycle model as native plugins:
  `init(context, proxy)` runs after the proxy is initialized and before Gate
  accepts connections.
- Surface Gate's entire in-scope public Go API without handwritten wrappers.
- Preserve typed values, methods, resources, callbacks, errors, and event
  mutation semantics across the component boundary.
- Keep the component contract language-neutral.
- Generate the WIT contract and both sides of the Go/Rust host bridge
  statically from Go type information.
- Fail generation when a new public declaration cannot be represented; never
  silently omit API.
- Require plugin authors to regenerate and rebuild after a breaking contract
  change. Gate will not carry compatibility shims for old contracts.
- Isolate plugins from Gate and from one another with memory, execution, handle,
  and capability limits.

## Non-goals

- Source compatibility with Gate's existing native `proxy.Plugin` mechanism.
- Loading existing native Go plugins as WebAssembly without adaptation.
- Gate-maintained Go, Rust, TypeScript, or other language SDKs.
- Browser or JavaScript-hosted WebAssembly using `syscall/js`.
- Dynamic reflection or JSON RPC as the normal host-call mechanism.
- ABI shims for plugins built against breaking older Gate contracts.
- Hot reload or unloading a single plugin in the first release.
- Unrestricted filesystem, network, process, environment, or clock access.
- Free-running guest goroutines or tasks while Gate is otherwise idle in the
  first release.

## Public API Scope

The generator will analyze every externally importable Gate library package:

- `go.minekube.com/gate/api/...`
- `go.minekube.com/gate/pkg/...`

It will exclude:

- Go `internal` packages, because they are not public API;
- `cmd/...` executable packages;
- tests, examples, generators, and development-only tools;
- the native plugin bootstrap declarations `proxy.Plugin` and
  `proxy.Plugins`, because WebAssembly components use the component lifecycle
  defined here instead.

The generator will also traverse types from other modules or the standard
library when they are reachable through an in-scope Gate signature. Those
types receive generated structural or resource representations sufficient to
preserve the reachable API. This does not independently expose unrelated APIs
from Gate's dependencies.

Every in-scope exported declaration must appear in the generated coverage
manifest as one of:

- a callable function or method;
- a value type, enum, flag set, alias, or resource;
- a constant or variable accessor;
- a callback contract;
- an automatically lowered language-neutral equivalent.

An unrepresented declaration is a generator error and fails CI. Any exceptional
exclusion must be explicit in the generator policy, include a reason in the
coverage manifest, and be reviewed as an API decision.

## Source Analysis and Canonical Model

The analyzer will use `golang.org/x/tools/go/packages` and `go/types`. A syntax
tree alone is insufficient because the generator needs resolved aliases,
embedded fields, method sets, instantiated generics, package identity, and
cross-package type relationships.

Analysis produces a deterministic canonical intermediate representation. Each
declaration records:

- stable package-qualified identity;
- Go kind and complete resolved signature;
- WIT name and lowered type;
- ownership and borrowing rules;
- nullability;
- error behavior;
- callback direction;
- documentation;
- dependencies on other declarations.

The canonical model is sorted independently of filesystem traversal and is the
only input to all generators. The following artifacts therefore cannot drift
from one another:

- the WIT package;
- Rust Wasmtime host traits and adapters;
- the Rust-to-Go C ABI definitions;
- Go dispatchers;
- API compatibility metadata;
- the export-coverage manifest.

Name conversion must be deterministic and collision checked. Package paths are
part of the canonical identity, so declarations with the same short Go name do
not collide.

## Go-to-WIT Type Lowering

The generator applies these rules recursively:

| Go shape | Component representation |
| --- | --- |
| booleans and fixed-width numbers | WIT scalar |
| `string` and `[]byte` | WIT `string` and `list<u8>` |
| named constants | typed accessor, enum, or flags where lossless |
| exported value structs | WIT records |
| pointers and stateful structs | typed WIT resources |
| interfaces | typed WIT resources with their method set |
| methods | resource methods or static functions |
| slices and arrays | WIT lists with explicit copy semantics |
| maps | lists of generated key/value records with explicit copy semantics |
| errors | typed `result` values with a common Gate error fallback |
| optional/nil values | WIT `option` |
| function values | callback identities and generated guest callback exports |
| channels | typed resources exposing supported send, receive, and close operations |
| `context.Context` | borrowed cancellable context resource |
| `time.Time` and durations | canonical timestamp and duration records |
| `any` | tagged dynamic value or typed opaque resource |
| generics | generated non-generic runtime equivalents or reachable monomorphizations |
| unsafe or non-inspectable identities | opaque typed resources |

Value records cross the boundary by copy. Pointers, interfaces, channels, and
other identity-bearing values cross as resources. A resource is not a raw Go
pointer; it is a generation-checked handle owned by one plugin.

Slice and map arguments are snapshots. Mutations made by a Go function are not
visible to the guest unless the API also returns the changed value. This copy
boundary is part of the generated contract and documentation.

For a reachable external type, the analyzer recursively includes the method set
needed to use values returned by Gate. Cycles are represented with resources,
not recursively expanded records.

If a type cannot be lowered without losing required behavior, generation stops
with a diagnostic naming the declaration and unsupported type path. Adding
such a declaration to Gate cannot silently reduce the WebAssembly API.

## Component Contract

The generated WIT world will expose package-grouped Gate interfaces and require
the plugin to export:

- plugin metadata containing name, version, and generated contract metadata;
- `init`, receiving borrowed context and proxy resources;
- generated callback entry points used by event, command, lifecycle, and timer
  registrations.

WIT does not pass Go closures directly. Guest bindings assign callback
identities and route host callback exports to guest-language closures or
handlers. This routing is described by the WIT contract and generated binding
shapes; it is not a Gate-specific handwritten SDK.

The initialization call is semantically:

```text
init(context, proxy) -> result<(), gate-error>
```

The context remains valid for the plugin lifetime and is canceled when Gate
shuts down. The proxy resource refers to the initialized Gate proxy. Both are
borrowed root resources and cannot be destroyed by the guest.

## Native Runtime Bridge

Gate will include a small Rust crate that uses Wasmtime's mature Component
Model API. Release binaries statically link this runtime through CGO; users do
not install a sidecar process or shared runtime.

The generated bridge uses direct C-compatible representations rather than JSON
or generic RPC:

- fixed-width scalars;
- `repr(C)` records;
- pointer/length pairs for transient strings and lists;
- numeric resource handles;
- explicit result and error discriminants;
- generated per-operation dispatch functions.

No Go pointer is retained by Rust. Input buffers are borrowed only for the
duration of a call. Cross-boundary output buffers use an explicit allocator and
free contract safe under CGO. Resource tables retain Go values on the Go side;
Rust and the component receive only typed numeric handles.

Panics may not unwind across the FFI boundary. Generated Go dispatchers recover
at the boundary, convert recoverable panics to a host error, attach diagnostic
context, and mark the plugin failed when continued execution would be unsafe.
Rust panics are likewise contained before returning through C.

The Rust crate owns:

- Wasmtime engine configuration;
- component compilation and instantiation;
- stores and store limits;
- WIT-generated host trait implementations;
- fuel and epoch interruption;
- guest export invocation;
- trap and backtrace normalization.

The Go runtime owns:

- access to real Gate values;
- generated API dispatch;
- plugin configuration and lifecycle;
- event and command registration;
- resource identity and lifetime policy;
- logging and user-facing diagnostics.

## Loading and Lifecycle

Gate will scan a configurable plugin directory, defaulting to `plugins/`, for
WebAssembly Components. Files load in deterministic filename order.

For each component, Gate will:

1. read and compile the component;
2. validate its exported plugin metadata;
3. validate its required Gate contract;
4. create an isolated Wasmtime store and resource table;
5. instantiate it with only allowed host interfaces;
6. call `init(context, proxy)`;
7. retain the instance until Gate shutdown.

This happens after the proxy is initialized and before it starts accepting
connections, matching the current native plugin initialization point. A load,
link, validation, or initialization error aborts Gate startup. Gate cancels the
lifetime context and performs deterministic plugin cleanup during shutdown.

Subscriptions, commands, timers, callbacks, and handles created by a plugin are
owned by that plugin. Shutdown removes registrations, cancels timers, invalidates
handles, and drops the store even if guest cleanup traps.

There is no per-plugin unload or hot reload in the first release.

## Contract Compatibility

Generated components embed:

- the canonical contract hash used to identify the exact source contract;
- a structural manifest of the imports they require;
- the generator format version.

The full contract hash changes whenever the generated contract changes. A hash
difference alone does not reject a plugin: Gate performs generated structural
compatibility validation.

Additive changes that preserve all imported shapes may remain loadable. A
removed or changed function, method, type, field, ownership rule, callback, or
error shape is breaking and causes a clear load-time rejection. Record shape
changes are breaking because records cross the boundary by value.

Gate does not emulate the old contract. After a breaking change, the plugin
author regenerates bindings against the new WIT package, updates their source
where required, and rebuilds the component.

Changing the generator's own ABI format is also breaking unless the generated
compatibility checker proves equivalence.

## Resources and Ownership

Each plugin instance has its own resource table. Every handle encodes or maps
to:

- owning plugin;
- resource type;
- generation;
- lifetime class;
- underlying Go value.

Using a handle from another plugin, with the wrong type, or after its generation
has expired returns a typed error. Handles are never globally transferable.

Resource lifetime classes are:

- **plugin**: valid until plugin shutdown or explicit drop;
- **owned**: guest may drop it and invalidate the handle;
- **borrowed call**: valid only for the active host or callback call;
- **borrowed event**: valid only while dispatching that event;
- **Gate-owned**: valid while the underlying Gate object remains registered or
  connected.

Generated adapters declare which class applies. Limits prevent a guest from
growing the table without bound.

## Calls, Concurrency, and Re-entrancy

Each plugin has a serialized executor associated with its Wasmtime store.
Concurrent Gate callbacks to one plugin are ordered through this executor.
Different plugins may execute concurrently.

Guest-to-host calls made during a guest invocation execute inline on the active
store. This preserves ordinary call/return behavior and avoids deadlock through
the executor queue.

A host call may synchronously cause Gate to publish another event that targets
the same plugin. Native plugins can observe this nested call immediately, so
the WebAssembly runtime must re-enter the active component rather than queueing
the nested callback until the outer call returns.

Nested same-instance Component Model re-entry, including borrowed resources,
traps, and interruption, is a mandatory feasibility gate. Implementation does
not proceed to full API generation until a focused spike proves:

- host call from an active guest invocation;
- synchronous nested callback into the same component;
- return to the original guest frame;
- correct borrowed-resource lifetime;
- correct trap propagation and cleanup.

If current Wasmtime APIs cannot support this safely, that is a blocking runtime
limitation requiring a design decision, not a behavior to silently weaken.

## Event Semantics

Gate events may be synchronous and mutable. For each event type, generation
produces:

- a typed borrowed event resource;
- getters for readable state;
- setters or operations for mutable state;
- a typed callback entry point.

Guest setters accumulate a transactional event patch. On successful callback
return, Gate applies the patch before invoking the next subscriber. If the
callback traps, times out, exhausts fuel, or returns an error, Gate discards the
entire patch. A later subscriber therefore sees either the complete committed
change or the original event, never a partial mutation.

The borrowed event handle expires when the callback returns. Retaining and
using it later yields an explicit expired-resource error.

## Commands, Timers, and Background Work

Command handlers and other function-valued registrations use the same typed
callback mechanism as events.

Go WebAssembly reactors do not continue running guest goroutines after an
exported call returns until the host calls into the component again. Standard
Go WIT async support is not yet available without a patched toolchain.
Therefore, the first release is event driven:

- plugin initialization returns;
- guest code runs for events, commands, lifecycle callbacks, and timers;
- Gate exposes one-shot and recurring timer registrations;
- timer callbacks enter the serialized plugin executor;
- no guest code runs while the component is idle.

This provides portable behavior across guest languages. Free-running async
guest tasks can be added later when the Component Model and guest toolchains
provide stable support.

## Failures

Failure behavior is divided by phase and severity:

- Load, link, metadata, compatibility, or `init` failure aborts Gate startup.
- Ordinary Gate API failures return typed WIT `result` values.
- A callback-returned error is logged with plugin and callback identity; its
  transactional mutations are discarded.
- A recoverable guest trap is logged with plugin, event or command identity,
  and the normalized Wasmtime backtrace; its mutations are discarded.
- Fuel exhaustion, deadline interruption, memory-limit breach, invalid runtime
  state, or another unrecoverable trap fails the plugin, removes all of its
  registrations, cancels its timers, and closes its store. Gate continues
  serving after runtime plugin failure.
- Invalid, foreign, mistyped, or expired handles return explicit errors and
  never expose host memory.

Logs and metrics must identify the plugin and operation without exposing other
plugins' data.

## Sandbox and Capabilities

Components receive only the generated Gate host interfaces by default. WASI
filesystem, sockets, environment, process, random, and ambient clock access are
denied unless Gate explicitly grants a capability in future configuration.

The initial release does not need capability grants. Gate-provided APIs such as
logging and timers remain available through the typed Gate contract.

Every plugin receives independent limits. Initial defaults are:

| Limit | Default |
| --- | ---: |
| guest linear memory | 128 MiB |
| data transferred by one host call | 16 MiB |
| live resource handles | 65,536 |
| scheduled timers | 1,024 |
| initialization deadline | 10 seconds |
| callback deadline | 100 milliseconds |
| Wasmtime fuel | enabled with a calibrated per-call budget |

Configuration may override these values per plugin. Limit validation rejects
negative, overflowing, or host-dangerous values. Memory limiting, fuel, and
epoch interruption are enforced in the Wasmtime store rather than relying only
on cooperative guest behavior.

## Configuration

The first configuration shape will support:

- enabling or disabling WebAssembly plugins globally;
- selecting the plugin directory;
- per-plugin enablement;
- per-plugin resource and deadline overrides.

Plugin identity comes from validated component metadata, not only the filename.
Duplicate identities fail startup. Unknown per-plugin configuration entries
produce a diagnostic so misspellings are not silently ignored.

The exact configuration syntax will follow Gate's existing configuration
conventions during implementation.

## Generated Artifacts

The implementation will keep source and generated responsibilities distinct:

```text
internal/wasm/
  analyze/          Go package/type analysis and canonical API model
  generate/         WIT, Rust, C ABI, Go dispatcher, and manifest generation
  runtime/          Go lifecycle, resources, executor, events, and limits
  runtime/native/   Rust Wasmtime host crate and generated bindings
  api/              generated contract artifacts
```

Final package names may be adjusted to match repository conventions, but the
dependency direction is fixed:

```text
Gate packages ← generated Go dispatchers ← runtime
canonical model → every generated artifact
runtime → native bridge → Wasmtime
```

Generated files contain a standard “DO NOT EDIT” header and the generator
version. Regeneration must be deterministic.

## Delivery Stages

### 1. Runtime feasibility

Build the smallest possible vertical component proving:

- Gate Go to Rust to WebAssembly and back;
- scalar, string, list, record, result, and resource transfer;
- guest-to-host calls;
- host-to-guest callbacks;
- synchronous nested same-component re-entry;
- fuel and deadline interruption;
- store and handle cleanup.

Failure of nested re-entry blocks the remaining design until resolved.

### 2. Analyzer and contract generator

Implement source loading, canonical type lowering, deterministic naming,
coverage reporting, WIT output, compatibility metadata, and regeneration
checks.

### 3. Complete Gate host surface

Generate the Rust host adapters, C ABI, Go dispatchers, resource operations,
callbacks, and errors for every in-scope declaration.

### 4. Product runtime

Implement configuration, discovery, lifecycle, event transactions, commands,
timers, isolation, diagnostics, metrics, limits, and release linkage.

### 5. Documentation and examples

Publish the generated WIT package and minimal Go and Rust example components.
Examples use upstream WIT bindgen tooling and demonstrate initialization,
logging, proxy lookup, an event mutation, a command, and a timer.

## Verification

CI will verify:

- every in-scope public declaration is represented or generation fails;
- the committed generated output has no diff after regeneration;
- declaration ordering and contract hashes are deterministic;
- the full hash changes when the canonical contract changes;
- structural compatibility accepts additive compatible changes and rejects
  breaking changes;
- the Rust host crate and CGO linkage build on every supported Gate release
  platform;
- example Go and Rust components compile and run;
- initialization receives working context and proxy resources;
- resource ownership, type, generation, expiration, and cross-plugin isolation;
- nested callbacks preserve call order without deadlock;
- successful event patches commit before the next subscriber;
- failed event patches are discarded;
- deadlines, fuel, memory, transfer, handle, and timer limits are enforced;
- denied WASI capabilities stay unavailable;
- startup failures abort cleanly;
- runtime plugin failures isolate and remove only the failed plugin;
- shutdown leaves no subscriptions, timers, stores, or handles behind;
- the complete existing Go test suite and release builds still pass.

## Risks

### Wasmtime re-entrancy

Nested same-component callbacks are essential for matching native synchronous
behavior and may conflict with Wasmtime store borrowing rules. The feasibility
stage answers this before broad generation work.

### Cross-platform release builds

The native Rust runtime adds CGO and platform-specific linking to Gate's release
pipeline. The feasibility stage must build representative supported targets,
and CI must cover the full release matrix.

### API size

Gate's public surface is large and includes hard boundary types. A canonical
model, generated coverage, and fail-closed lowering prevent partial support but
will expose unsupported cases early. Generator work is accepted only when the
coverage manifest is complete.

### Guest-language maturity

WIT tooling differs by language, and Go's asynchronous component support is
still developing. The core contract remains language-neutral; the event-driven
model avoids depending on unstable async support.

### Runtime overhead

Serial execution, resource validation, copied value types, and transactional
events add overhead. Benchmarks in the feasibility stage will establish call
cost and guide fuel and deadline defaults without weakening isolation.

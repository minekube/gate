# pkg/internal/reload agent notes

Config reload correctness must not rely on fsnotify delivery alone: `pkg/internal/reload/watch.go` reconciles content fingerprints because macOS can miss delete/recreate events. On Windows, fingerprint handles must allow delete sharing or an editor's atomic replacement fails with access denied, so open-handle replacement coverage uses `ReplaceFileW` (`fingerprint_replace_test_windows.go`). Beyond that, replacing the config while the watcher reads it is a platform problem, not a watcher bug: `os.Rename` (MoveFileEx `MOVEFILE_REPLACE_EXISTING`) is refused with `Access is denied` against *any* open handle on the destination, whatever its share mode, and the watcher cannot hash the file without opening it (measured on windows-latest: 1319/3000 write+rename attempts failed with the watcher running, 0/3000 with it stopped). Tests that replace a watched config must therefore retry that transient sharing violation (`replace_config_test_windows.go`) instead of calling `os.Rename` directly - and not via `ReplaceFileW`, which drops the destination name mid-swap and so is reported as a second reload where the burst must coalesce into one. Preserve its single-owner loop and silent-watcher regression coverage when changing debounce or watcher behavior.

The same delete-sharing opener backs config content reads (`ReadConfigFile` in `config_read.go`, used by `pkg/gate/gate.go`), because a read that does not share delete refuses an operator's `ReplaceFileW` config save for as long as it is in flight; `config_read_windows_test.go` measures that against the loader shape (replacement refusals must be zero while reads loop). That covers the startup discovery too: `cmd/gate`'s `initViper` resolves the `config.*` file viper's search would pick and names it on viper with `SetConfigFile` (`findDefaultConfigFile`), so the file Gate starts on is read once, by Gate. Viper's own `ReadInConfig` - afero -> `os.ReadFile`, no delete sharing - is still reachable when a config file is not where viper's search looks (`ReplaceFileW` has the name away for part of its swap, so Gate's startup discovery can see no file and fall back), which is why Gate loads config through `gate.NewViper`, whose file system serves reads with `OpenConfigFile`, this package's delete-sharing opener (`ConfigFileSystem`). Reads of a config file therefore share delete whichever side makes them; only a caller that loads with a plain `viper.New()` keeps the unguarded read.

The same discipline applies on every platform, for a second reason: the watcher reports every content state it can observe, so a fixture that writes a watched config in place (`os.WriteFile`: O_TRUNC, then the bytes) exposes the destination's truncated state as a change of its own. On a loaded runner the writer is descheduled between those two syscalls, the watcher's debounce elapses before the bytes land, and the settled content is then reported as a second reload - a coalescing fixture failed with `expected: 1 actual: 2` on ubuntu-latest (run 36328594414) exactly that way. Fixtures therefore write watched configs with `replaceWatchedConfig` (temporary file + `replaceConfigFile`), and `TestWatchCoalescesIdenticalWritesAcrossADebounceWindow` keeps the straddle (a burst whose later writes land after the first reload was reported) forced with event handoffs rather than slept for.

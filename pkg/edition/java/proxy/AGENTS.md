# pkg/edition/java/proxy agent notes

Secure-chat acknowledgement state is maintained in `pkg/edition/java/proxy/chat_queue.go` and driven by the handlers in `handle_cmd.go`/`handle_chat.go`; it is a direct port of Velocity (`ChatQueue`, `SessionCommandHandler`), which is the reference for correct behavior. The `LastSeenMessages.Offset += delayedAckCount` adjustment is intentional and matches Velocity - not dead code - so validate any change against Velocity's source and a proxy-level reproduction. Key invariant: an `UnsignedPlayerCommand` (1.20.5+, commands with no signable args - the common path in offline mode) carries NO last-seen update, so it must not be fed into the chat queue (that flushes and discards the player's held acknowledgements) and must be forwarded command-only; a consumed command's `ChatAcknowledgement` gates on the offset, not the acknowledged bitset. Regression coverage: `handle_cmd_ack_test.go`.

Duplicate-login handling lives in `Proxy.canRegisterConnection`/`registerConnection`/`unregisterConnection` (`pkg/edition/java/proxy/proxy.go`) and decides whether a reconnecting player is refused with "You are already connected to this server!". Two invariants: (1) unregistration is **value-scoped** (a port of Velocity's `connectionsByName.remove(name, player)`), so a connection that lost the registration race - e.g. a refused duplicate whose teardown runs after the winner registered - can never evict the player that owns the slot now; (2) only a registration that can still be a live player session blocks a newer connection. A registration whose connection is already closed, or that never reached play (still logging in / connecting to its first backend - the shape of an abandoned attempt after a client timeout, a pre-play kick, or a half-open connection that was not reaped), is **superseded** by the newer connection; anything placed on a backend (Play state or a current server connection, including a server switch through the configuration state) is never displaced. This is the Connect-edge failure that refused fast reconnects for nine players on seven machines plus the `MinekubeK8s` join prober; upstream Velocity has no supersede rule and refuses those reconnects. Regression coverage: `duplicate_login_test.go`.

Every dynamically allocated loopback listener must come from `pkg/util/loopback` (`loopback.Default().Listen()`), never `net.Listen("tcp", "127.0.0.1:0")`. The vialite supervisor reserves a dynamic backend's port with a listen-then-close before the runtime binds it, so a listener drawn from the kernel's ephemeral range can take that port: the child dies with "Address already in use", readiness (a plain dial) is satisfied by the foreign listener, and the join is routed into another session's tunnel where it stalls silently in configuration state. Gate's per-join translation bridge (`newViaBackendBridge`) was that listener, and readiness alone cannot tell "the runtime answers" from "something answers" - so `viaManagedRunner.BackendDialAddress` also refuses a runtime-published dynamic backend address unless it is that backend's own bridge or provably outside Gate's ownership (`checkPublishedBackendAddress`). `pkg/util/loopback` is exported so moxy allocates its dynamic loopback listeners from the same ranges. Regression coverage: `vialite_loopback_test.go`, `pkg/util/loopback/loopback_test.go`.
